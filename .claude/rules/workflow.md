# 実装ワークフロー制御

## 基本原則

- **Simplicity First**: 全ての変更を可能な限りシンプルにする。影響範囲を最小限にする
- **No Laziness**: 根本原因を見つける。一時的な修正をしない。シニア開発者の水準を保つ
- **Minimal Impact**: 必要な箇所のみ変更する。バグの混入を避ける

## スキル優先原則（Skills First）

- タスクに着手する前に、`.claude/skills/` の既存スキルで解決できないかを**最初に**確認する
- 特に以下の操作は必ずスキルを使う:
  - コミット → `/git-manager`
  - バグ修正 → `/bugfix`
  - 機能開発 → `/feature`
  - コードレビュー → `/review`
  - セキュリティ監査 → `/security-audit`
  - 仕様書作成 → `/spec`
- スキルが存在するのに手動で同じことをしない — スキルには検証ステップや best practice が組み込まれている

## プランモードの活用

- 3ステップ以上または設計判断を伴うタスクは必ずプランモードで開始する
- 実装中に問題が発生した場合は即座に中断して再計画する — 無理に進めない
- 検証ステップもプランに含める
- 事前に詳細な仕様を記述して曖昧さを減らす

## サブエージェント戦略

- メインのコンテキストウィンドウをクリーンに保つためにサブエージェントを積極活用する
- 調査・探索・並列分析はサブエージェントに委譲する
- 複雑な問題にはサブエージェントで計算リソースを投入する
- 1サブエージェントにつき1タスクで集中して実行する

## 自己改善ループ

- ユーザーからの修正指示があった場合は、`tasks/lessons.md` に同じ間違いを防ぐルールを追記する
- ルールは具体的で再現可能な形式で記述する
- 新しいセッション開始時には `tasks/lessons.md` を確認する

## 完了前の検証

- テスト実行・ログ確認で動作を証明するまでタスクを完了としない
- 必要に応じて main ブランチとの差分を確認する
- 「シニアエンジニアがこの変更を承認するか？」を自問する

## エレガントさの追求（バランス重視）

- 非自明な変更では「もっとエレガントな方法はないか？」と一度立ち止まる
- ハック的な修正に感じたら「今知っていることを踏まえた最善の実装」を選択する
- シンプルで明白な修正にはこのルールを適用しない — 過度な設計をしない

## バグの自律修正

- バグ報告を受けたら質問せずにまず修正に着手する
- ログ・エラー・失敗テストを確認し、それらを解決する
- ユーザーのコンテキストスイッチを最小限にする

## 実装タスク管理

1. **Plan First**: `tasks/todo.md` にチェックリスト形式で計画を記述する
2. **Verify Plan**: 実装開始前にユーザーと計画を確認する
3. **Track Progress**: 進行中に各項目を完了マークする
4. **Explain Changes**: 各ステップで変更の概要を説明する
5. **Document Results**: 結果を `tasks/todo.md` のレビューセクションに記録する
6. **Capture Lessons**: ユーザーからの修正後に `tasks/lessons.md` を更新する
