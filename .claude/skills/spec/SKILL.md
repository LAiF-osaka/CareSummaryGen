# 実装仕様書生成ワークフロー

`$ARGUMENTS` に指定されたモジュール・ディレクトリに対して、詳細な実装仕様書を `docs/` に生成してください。

## 進め方

### Phase 1: スコープ確認

`$ARGUMENTS` を解析して対象モジュールを特定する。
未指定の場合はプロジェクトルートを対象とする。

代表的な呼び出し例:
- `/spec` → プロジェクト全体の仕様書
- `/spec app.py` → メインアプリケーションの仕様書
- `/spec services/` → 特定モジュールの仕様書

### Phase 2: 徹底調査（最重要フェーズ）

以下を実施する。**調査は手を抜いてはならない**:

1. 対象ディレクトリ以下の全ファイルをGlobで列挙する
2. 全ファイルを Read ツールで読む（省略不可）
3. docs/ 以下の既存ドキュメントをすべて読み、プロジェクトの背景・目的を把握する
4. CLAUDE.md を読んで全体方針を把握する
5. 型定義・モデル定義ファイルを特に詳しく読む
6. 通信フロー・状態遷移を正確に把握する

執筆すること:
- 品質基準（完全性・正確性・深度・可読性）を満たす仕様書
- ファイル名は対象モジュールを表す日本語名（例: アプリケーション実装仕様書.md）
- docs/ ディレクトリに Write ツールで保存する

品質チェック（出力前に自問すること）:
- 読んでいないファイルはないか？
- すべての公開インターフェースを記述したか？
- 「なぜ」の説明を含めたか？
- 実際のコードと一致しているか？
- エラーケース・エッジケースを記述したか？

### Phase 3: 品質確認

生成した仕様書を読み、以下を確認する:

**完全性チェック**:
- [ ] 目次が存在し、全章へのリンクがある
- [ ] 型定義・モデル定義が網羅されている
- [ ] 全APIエンドポイントが記述されている
- [ ] 環境変数一覧がある
- [ ] エラーハンドリングが記述されている

**精度チェック**:
- [ ] モデル定義が実装コードと一致しているか
- [ ] APIエンドポイントパスが実装と一致しているか
- [ ] フロー図の処理順序が実装と一致しているか

不足がある場合は追記・修正する。

### Phase 4: 完了報告

ユーザーに以下を報告する:
1. 生成した仕様書のパス（クリッカブルリンク形式）
2. 仕様書の章構成サマリ（目次）
3. 主要な調査発見事項（仕様書に記載した重要なアーキテクチャ上の判断・制約）
4. 既存ドキュメントとの差異・補完関係

## 注意事項

- 対象のコンテキストは具体的に（ファイルパス・ディレクトリ名を明示する）
- 既存の仕様書がある場合は「既存の〇〇.md を参照した上で、重複しないよう補完する形で執筆」と指示する
- 仕様書は「いつ誰が読んでも実装できる」水準を目指す——「なんとなく分かる」では不十分
