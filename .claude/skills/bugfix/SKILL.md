# Bug Fix Workflow

`$ARGUMENTS` に記述されたバグを修正してください。

## 進め方

### Phase 1: バグの再現と分析
以下を実施:
- `$ARGUMENTS` のバグを再現するステップを確立する
- 現在 FAIL する pytest テストを作成する
- バグの原因箇所を特定する

### Phase 2: 修正実装
分析結果に基づき修正を実装する。

失敗テストと再現条件を必ず確認すること。

### Phase 2.5: リファクタリングチェック（必須）

**このフェーズは省略不可。** 修正コードの品質を確認する。

1. **チェック項目**:
   - ファイルが300行を超えていないか
   - 修正が適切なレイヤーに配置されているか
   - **Docstring 規約**: 新規・変更した公開 API に docstring があるか（Python: Google Style）

2. 違反があれば修正してから Phase 3 へ

### Phase 3: 修正確認
以下を実施:
- 修正コードの品質確認
- 失敗テストが PASS になること、回帰テストが通ることを確認
  ```bash
  uv run pytest
  ```

### Phase 4: バージョン管理
全確認が完了したら:
- `bugfix/<バグ名>` ブランチを作成
- `fix(scope): [バグの説明]` でコミット（Conventional Commits）
- PR を作成

### Phase 5: ポストモーテム作成
重大度 Medium 以上のバグの場合、`docs/postmortems/YYYY-MM-DD_<kebab-case>.md` にポストモーテムを作成する。

以下を記録:
- **根本原因**: なぜこのバグが発生したか
- **タイムライン**: 検知〜修正〜検証の経緯
- **影響**: ユーザー・サービスへの影響範囲
- **学び**: やって良かったこと、改善すべきこと、今後のルール

軽微な typo 修正やスタイル調整のみのバグは Phase 5 をスキップしてよい。

## 完了報告

1. 修正した内容のサマリ
2. 修正前後の動作の違い
3. テスト結果（失敗→成功のレポート）
4. ブランチ/コミット情報
5. ポストモーテム（作成した場合はファイルパス）
