# 設計書リファクタワークフロー

`$ARGUMENTS` に従い、既存の設計書（`docs/`）をリファクタして品質・フォーマットを統一してください。

**注意**: このスキルは既存ドキュメントの「リファクタ・品質統一」に特化する。ゼロからの仕様書生成は `/doc-writer` を使うこと。

## モードの判定

`$ARGUMENTS` の先頭トークンで実行モードを判定する:

| 先頭トークン | モード | 動作 |
|-------------|--------|------|
| `lint` | 検証モード | 違反箇所を検出・レポートするのみ。ファイル変更しない |
| `fix` | 修正モード | 違反箇所を検出し、自動修正する |
| 省略 | 修正モード | デフォルトは `fix` |

第2トークン以降はスコープ（ファイルパスまたはディレクトリ）:

```
/doc-refactor lint                    # 全ファイルの違反検出
/doc-refactor lint docs/              # docs ディレクトリの検証
/doc-refactor fix docs/設計.md        # 指定ファイルを修正
/doc-refactor docs/                   # ディレクトリ一括修正（fix省略）
/doc-refactor                         # 全ファイル一括修正
```

## 検証ルール

以下のルールで違反を検出する。重要度は Critical > Warning > Info。

### Critical（必須修正）

| # | ルール | 検出方法 |
|---|--------|---------|
| C1 | 全ての図が `\`\`\`mermaid` であること — ASCII art / plaintext の擬似図は禁止 | `\`\`\`text` / `\`\`\`plaintext` / `\`\`\`` ブロック内に罫線文字（┌│└├─→←↓↑▶▼▲◆●○■□）が含まれるか |
| C2 | 目次が存在し、各セクションへのアンカーリンクがあること | `## 目次` セクションの存在と `[xxx](#xxx)` リンクの有無 |

### Warning（推奨修正）

| # | ルール | 検出方法 |
|---|--------|---------|
| W1 | セクション 1「背景・目的」が存在すること | `## 1. 背景・目的` の有無 |
| W2 | 末尾セクションに「関連ドキュメント」があること | 最後の `##` が「関連ドキュメント」を含むか |
| W3 | `<!-- -->` テンプレートプレースホルダが残っていないこと | HTML コメントの検出 |

### Info（改善提案）

| # | ルール | 検出方法 |
|---|--------|---------|
| I1 | ファイルサイズが 3000行を超えていないこと | 行数カウント |

## 実行フロー

### Phase 1: スコープ特定と現状スキャン

1. `$ARGUMENTS` からモードとスコープを解析する
2. スコープ未指定なら `docs/` 配下の全 `.md` ファイルを対象とする
3. 対象ファイルを Glob で列挙する

### Phase 2: 検証（lint）

各対象ファイルを Read で読み込み、全ルール（C1-C2, W1-W3, I1）をチェックする。

結果を以下の形式でレポートする:

```
## Lint Report

### docs/設計.md
- ❌ C1: ASCII art 図が 3箇所（L120, L245, L380）
- ⚠️ W2: 末尾に「関連ドキュメント」セクションなし

### サマリ
| 重要度 | 件数 |
|--------|------|
| Critical | 3 |
| Warning | 1 |
| Info | 0 |
```

**lint モードの場合はここで完了**。ユーザーにレポートを提示して終了する。

### Phase 3: 修正（fix モード）

**1ファイルずつ順番に処理する**（並列修正しない）。

対象ファイルを Read で全文読み込み、以下の順序で修正する:

**Step A: ASCII art → Mermaid 変換（C1 — 最重要）**

| 元の図の種類 | 変換先 Mermaid タイプ |
|-------------|---------------------|
| フロー図 | `graph TD` または `graph LR` |
| シーケンス | `sequenceDiagram` |
| 状態遷移 | `stateDiagram-v2` |
| アーキテクチャ図 | `graph TD` |
| ツリー構造 | `graph TD` |

**変換しないもの（例外）**:
- ディレクトリツリー（`├── src/` 形式）→ ```` ```text ```` のまま可
- コードスニペット（Python / YAML 等）→ そのまま
- Markdown テーブル → そのまま
- コマンド例（`$ uv run ...`）→ ```` ```bash ```` のまま

**Step B: 目次の整備（C2）**
- 目次がなければ追加
- 既存の目次があればセクション番号とアンカーリンクを検証・修正

**Step C: セクション構造の正規化（W1-W3）**
- 「背景・目的」「関連ドキュメント」がなければ追加（空セクションでも枠だけ作る）
- テンプレートプレースホルダ（`<!-- -->`）を削除

**Step D: 保存**
- Write ツールで上書き保存
- 変更箇所のサマリをユーザーに報告

### Phase 4: 検証（修正後 lint）

修正したファイルに対して Phase 2 の lint を再実行し、Critical 違反がゼロであることを確認する。
残存違反があれば再修正する。

### Phase 5: 完了報告

ユーザーに以下を報告する:

1. **修正ファイル一覧**（クリッカブルリンク形式）
2. **修正サマリ**:
   - Mermaid 変換数（ASCII art N箇所 → Mermaid N図）
   - セクション追加数
3. **Before / After 統計**:
   - Critical 違反数（修正前 → 0）
4. **残存 Warning / Info**（あれば）

## 注意事項

- **内容は変更しない**: リファクタは「フォーマット・図・構造」のみ。技術的な記述内容は一切変更しない
- **情報の欠落禁止**: ASCII art → Mermaid 変換で元の情報が失われていないか必ず確認する
- **1ファイルずつ**: 大量修正でも1ファイルずつ処理し、各ファイルの修正後に lint 再実行する
