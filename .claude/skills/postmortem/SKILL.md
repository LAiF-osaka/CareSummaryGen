# Postmortem Workflow

バグ修正・インシデント対応・パフォーマンス問題など、対処が完了した不具合のポストモーテムを作成する。

## 入力

`$ARGUMENTS` にインシデントの説明、PR番号、またはコミットハッシュが渡される。

## 進め方

### Phase 1: 情報収集

1. `$ARGUMENTS` の内容を解析する
   - PR番号が指定された場合: `gh pr view <番号>` で変更内容を取得
   - コミットハッシュの場合: `git show <hash>` で変更内容を取得
   - 説明テキストの場合: そのまま使用
2. 関連する git diff を確認し、変更されたファイルと変更内容を把握する
3. 関連するログ・エラーメッセージがあれば収集する

### Phase 2: テンプレートに基づくドキュメント作成

`docs/postmortems/TEMPLATE.md` のフォーマットに厳密に従って作成する。

**ファイル名**: `docs/postmortems/YYYY-MM-DD_<kebab-case-title>.md`

**必須セクション**:

| セクション | 内容 |
|-----------|------|
| メタデータ | 日付、重大度(Critical/High/Medium/Low)、影響範囲、対応時間、担当 |
| 概要 | 1-2文で何が起きたかを要約 |
| タイムライン | 検知〜解決の時系列（テーブル形式） |
| 根本原因 | 技術的な根本原因を明確に記述 |
| 影響 | ユーザー・サービスへの影響 |
| 即時対応 | 実施済みの対策 |
| 恒久対策 | TODO形式の再発防止策 |
| 学び | やって良かったこと / 改善すべきこと / 今後のルール |
| 関連リンク | PR、実装方針ドキュメント等 |

### Phase 3: 品質チェック

作成したポストモーテムを以下の観点でセルフレビューする:

- [ ] 根本原因が「何が起きたか」ではなく「なぜ起きたか」を説明しているか
- [ ] 恒久対策が具体的で実行可能か（「気をつける」のような曖昧な記述は不可）
- [ ] 学びのセクションに再発防止のルールが含まれているか
- [ ] 関連リンク（PR、ファイルパス等）が正確か

### Phase 4: lessons.md への追記

ポストモーテムの「今後のルール」セクションから、汎用的なルールを `tasks/lessons.md` に追記する。
既に同様のルールが存在する場合はスキップする。

## 重大度の判断基準

| 重大度 | 基準 |
|--------|------|
| Critical | 本番サービス停止、データ損失 |
| High | 主要機能の利用不可、セキュリティ脆弱性 |
| Medium | 機能の一部が利用不可、ワークアラウンドあり |
| Low | 軽微な不具合、UX上の問題 |

## 注意事項

- 軽微な typo 修正等（重大度 Low 未満）ではポストモーテムは不要
- 非難ではなく改善に焦点を当てる（blameless postmortem）
- 技術的に正確であること。推測はそう明記する
