# 設計書生成ワークフロー

`$ARGUMENTS` に指定されたモジュール・ディレクトリに対して、設計書を新規作成してください。

**注意**: このスキルは「ゼロからの設計書の新規作成」に特化する。既存ドキュメントのリファクタ・品質統一は `/doc-refactor` を使うこと。

## /doc-writer と /doc-refactor の使い分け

| スキル | 用途 | 入力 | 出力 |
|--------|------|------|------|
| `/doc-writer` | 新規作成 | モジュール/ディレクトリパス | `docs/` に新規 .md |
| `/doc-refactor` | 既存リファクタ | `lint` or `fix` + ファイルパス | 既存 .md の上書き修正 |

## 進め方

### Phase 1: スコープ確認

`$ARGUMENTS` を解析して対象モジュールを特定する。
未指定の場合はプロジェクト全体を対象とする。

### Phase 2: 徹底調査（最重要フェーズ）

以下を実施する。**調査は手を抜いてはならない**:

■ 必須読み込み（省略不可）
1. CLAUDE.md — 全体方針
2. docs/ 以下の既存ドキュメント — 背景・目的の把握、重複回避

■ 調査すること
1. 対象ディレクトリ以下の全ファイルを Glob で列挙する
2. 全ファイルを Read ツールで読む（省略不可）
3. 型定義・モデル定義ファイルを特に詳しく読む
4. 通信フロー・状態遷移を正確に把握する

■ 執筆ルール（厳守）

図の記述:
- 全ての図は ```mermaid で記述すること（ASCII art / plaintext 図は禁止）
- フロー図 → graph TD / graph LR
- シーケンス図 → sequenceDiagram
- 状態遷移 → stateDiagram-v2
- 日本語ノードラベルは ["ラベル"] で括る
- 例外: ディレクトリツリー（```text）、コードスニペット、コマンド例はそのまま

内容:
- 品質基準（完全性・正確性・深度・可読性）を満たす
- ファイル名は対象モジュールを表す日本語名
- docs/ ディレクトリに Write ツールで保存する

品質チェック（出力前に自問すること）:
- 読んでいないファイルはないか？
- すべての公開インターフェースを記述したか？
- 「なぜ」の説明を含めたか？
- 実際のコードと一致しているか？
- エラーケース・エッジケースを記述したか？
- ASCII art の図が1つも残っていないか？（→ 全て Mermaid であること）

### Phase 3: 品質確認

生成した設計書を読み、以下を確認する:

**完全性チェック**:
- [ ] 型定義・モデル定義が網羅されている
- [ ] 全 API エンドポイントが記述されている（該当する場合）
- [ ] 環境変数一覧がある（該当する場合）
- [ ] エラーハンドリングが記述されている

**精度チェック**:
- [ ] モデル定義が実装コードと一致しているか
- [ ] API エンドポイントパスが実装と一致しているか
- [ ] フロー図の処理順序が実装と一致しているか

不足がある場合は追記・修正する。

### Phase 4: 完了報告

ユーザーに以下を報告する:
1. 生成した設計書のパス（クリッカブルリンク形式）
2. 設計書の章構成サマリ（目次）
3. 主要な調査発見事項（重要なアーキテクチャ上の判断・制約）
4. 既存ドキュメントとの差異・補完関係
5. Mermaid 図の数

## 注意事項

- 対象のコンテキストは具体的に（ファイルパス・ディレクトリ名を明示する）
- 既存の設計書がある場合は「既存の〇〇.md を参照した上で、重複しないよう補完する形で執筆」と指示する
- 設計書は「いつ誰が読んでも実装できる」水準を目指す——「なんとなく分かる」では不十分
- **図は全て Mermaid**: これは品質基準の最重要項目。ASCII art は一切許容しない
